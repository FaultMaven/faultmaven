# Knowledge Base Ingestion Architecture

**Document Type:** Component Specification
**Version:** 2.0
**Last Updated:** 2026-06-09

---

## Purpose

This document specifies **how runbook content reaches the FaultMaven Knowledge Base**: the two distinct ingestion paths, the atomicity guarantees each provides, and the operational rules that prevent ingestion drift between the SQL source-of-truth and the ChromaDB vector store.

It complements:

- [`kb-pack-architecture.md`](./kb-pack-architecture.md) — the **KB pack** artifact ingested by Path 1: its format, the `KB_PACK_DIR` contract, how it's built, and how it's delivered.
- [`knowledge-base-architecture.md`](./knowledge-base-architecture.md) — storage and retrieval (the *what*).
- [`document-to-runbook-conversion.md`](./document-to-runbook-conversion.md) — how arbitrary documents get converted into runbook drafts.

---

## Why two ingestion paths?

A runbook can enter the KB through one of two flows. They share the **same destination tables** (`knowledge_items` + ChromaDB chunks) but originate from very different sources, and conflating them produced the bug history this design exists to prevent.

| Path | Source | Trust level | Needs human review? |
|------|--------|-------------|---------------------|
| **Bootstrap (pre-deployed)** | The **KB pack** (`resources/knowledge/pack`, or `KB_PACK_DIR`) — shipped runbooks + build-time vectors | High (platform-vetted) | No |
| **Conversion (draft → verify)** | Generated by LLM from case evidence or uploaded docs | Low until reviewed | Yes (via Dashboard "Verify" UI) |

Pre-deployed runbooks are already authored, validated, and scored — and embedded — by build time. Forcing them through the `conversion_drafts` table — and through the per-user "Activate" UI — is ceremony without value. The conversion path exists specifically because case-generated drafts need a human gate. Bootstrap runbooks don't.

## Path 1 — Bootstrap (`faultmaven/bootstrap/kb_init.py`)

### Trigger

Runs once at API startup, immediately after the DI container has wired up `KnowledgeService`. Implementation: `bootstrap_kb()` called from `main.py` lifespan (see search for `KB Bootstrap` block).

### Source: the KB pack (not the embedding model)

Bootstrap ingests the **KB pack** — a self-contained bundle of runbooks +
build-time vectors loaded via `KbPack.load(KB_PACK_DIR)`. Because every chunk
ships its **text and its vector** in the pack, **ingestion itself uses no
embedding model and no chunking** — pure SQL + ChromaDB writes. This is what turns
~tens of minutes of on-pod CPU embedding into seconds (see
[`kb-pack-architecture.md`](./kb-pack-architecture.md)). The BGE-M3 model *is*
still loaded once at boot (~5s) — from the cache **baked into the image** (CPU-only
torch, `HF_HUB_OFFLINE`/`TRANSFORMERS_OFFLINE`, so no HuggingFace fetch — works
air-gapped) — but it serves *query-time* search and the conversion/verify path; the
pre-embedded pack is ingested without it. Built-ins are no longer copied to `data/knowledge/global` — that directory
is now solely the workspace for authored/converted runbooks and `/knowledge/scan`.

### Algorithm

1. Resolve the pack directory from `KB_PACK_DIR` (default: bundled baseline at `resources/knowledge/pack`) and `KbPack.load()` it. A missing/corrupt pack logs a warning and yields an empty result — it does not crash startup.
2. For each runbook in the pack:
    - `item_id` is carried by the pack (= `kb_{sha256(runbook_id)[:12]}`).
    - Compare the pack's `content_hash` against the existing `knowledge_items.content` row.
        - **Match** → skip; record `skipped_unchanged`.
        - **Mismatch** → delete old SQL row + ChromaDB chunks for this `item_id`, then re-ingest.
        - **No existing row** → ingest fresh.
3. Call `KnowledgeService.ingest_runbook(prechunked=[(text, vector), ...], verified_by=None, verification_level=COMMUNITY, ...)`. With `prechunked` supplied, the SQL row is written and the pack's chunk texts + vectors are written to ChromaDB directly — **no `ContentChunker`, no `model.encode`**. `verified_by` is an FK to `users.user_id` and must be a real user or `NULL` — **never a sentinel string**. Platform-shipped trust is expressed through `verification_level=COMMUNITY`, not a fake `verified_by` (a previous `verified_by="system"` violated the FK once `foreign_keys=ON` was enabled and failed every shipped-runbook ingest). Tags are coerced to strings on the way in — a bare numeric YAML tag such as `503` parses as `int`, and both the relational `KnowledgeItem` and the ChromaDB `KnowledgeBaseDocument` require `str` tags.
4. If `chunks_created <= 0` or the call raised, the failure is recorded in `BootstrapResult.failed` and the next runbook is processed (single-runbook failures must not block the others).
5. **Prune orphaned built-ins.** After the loop, delete any built-in `knowledge_items` row (deterministic `kb_<12 hex>` id) not present in the current pack — typically because a runbook was removed from the pack or its frontmatter `id` changed, leaving the old deterministic row behind. Recorded in `BootstrapResult.pruned`.
6. **Reconcile the two stores + repair orphans** (`_reconcile_vectors` → `_repair_orphaned_rows`). The prune is keyed off SQL rows, so it is structurally blind to drift where the two stores disagree. This pass compares both sides:
    - **Orphaned vectors** — a ChromaDB parent with no `knowledge_items` row. Deleted (batched), but **only for built-in `kb_<12 hex>` ids** — the shared `faultmaven_kb` collection holds every tenant's vectors while the RLS-scoped row query sees one tenant's rows, so unbounded deletion would wipe other tenants. Recorded in `BootstrapResult.orphaned_vectors_cleaned`.
    - **Orphaned rows** — a `knowledge_items` row with no vectors (the half-state a crash between the SQL commit and the ChromaDB write leaves; silently non-retrievable). A **bounded** repair re-chunks + re-embeds the row's persisted `content` with BGE-M3 and writes only the vector store (`KnowledgeService.reindex_missing_vectors`) — the SQL row, the source of truth, is never touched. Repaired ids → `BootstrapResult.repaired_rows`; any that could not be repaired (embedding model unavailable, ChromaDB error) stay in `BootstrapResult.orphaned_rows` and are re-attempted next boot. Repair only **adds** a row's own vectors, so — unlike the delete side — it is cross-tenant-safe and eligible for **all** orphaned rows (authored as well as built-in). It is bounded twice: `KB_REPAIR_MAX_ROWS` (25) treats a larger orphan set as a bulk-loss anomaly (e.g. the vector collection was wiped) and repairs nothing (recovery there is a full pack re-ingest); `KB_REPAIR_MAX_CHUNKS` (60) caps the embedding **work** per boot, since this repair runs on the lifespan startup path *before the app serves readiness* and the timeout risk is chunk count × pod CPU, not row count — rows past the budget defer to the next boot (per-row vectors persist, so repair is incremental). This is the one bootstrap step that **loads the embedding model**, and only when there is at least one orphaned row (rare), so the fast model-free boot is preserved in the common case.

      > **Ops note.** Both bounds are configurable per deployment via `KB_REPAIR_MAX_ROWS` / `KB_REPAIR_MAX_CHUNKS` (env → `DatabaseSettings`; defaults 25 / 60 in `faultmaven/bootstrap/kb_init.py`). Which path runs the repair depends on the tenancy provider, **not** on cloud-vs-self-hosted (both run the same unified codebase and can be multi-tenant): under a single-tenant `TENANT_PROVIDER` the web-startup bootstrap runs the repair on the lifespan critical path *before readiness*, so a repair of up to `KB_REPAIR_MAX_CHUNKS` chunks (plus the model load) delays startup — lower the budget (or widen a tight k8s `startupProbe`) if needed. Under `TENANT_PROVIDER=multi` the web bootstrap is skipped entirely and repair runs in the `kb_seed` maintenance job, off the readiness path.

### Atomicity

`ingest_runbook` now treats a 0-chunk result as a failure and rolls back its just-created SQL row (see [`knowledge_service.py: _delete_knowledge_item_row`](../../../faultmaven/modules/knowledge/domain/services/knowledge_service.py)). The combined invariant: **on any failure, no half-state remains in either store.** Callers can rely on:

- Exception raised → nothing persisted.
- Normal return → both stores updated; `chunks_created > 0`.

### Idempotency

Bootstrap is safe to re-run on every restart:

- Unchanged runbooks are detected by content hash → no work, no churn.
- Changed runbooks trigger explicit delete-then-ingest.
- New runbooks are added.
- **Built-ins are pack-reconciled (add / skip / prune).** A built-in row (`kb_<12 hex>` id) not present in the current pack — because the runbook was removed or its `id` changed, orphaning the old deterministic id — is pruned at the end of bootstrap (step 5). **The pack is the source of truth for built-in content.**
- **Authored/user content is never auto-removed.** Items created by `verify_draft` or the API carry random-UUID ids, which the `kb_<12 hex>` prune pattern cannot match — so the prune is structurally incapable of touching them. Removing those is the Dashboard's explicit delete path. Operators who need a full reset use `fm-reset-kb`.
- **Safety guard:** if the pack yields zero runbook ids (a load/parse anomaly, not a legitimate "remove everything"), the prune is skipped entirely.
- **Self-healing across stores.** A row left without vectors by a mid-ingest crash is re-embedded on the next boot (step 6), so a rare crash between the SQL commit and the ChromaDB write does not permanently strand a runbook as silently unretrievable — subject to the `KB_REPAIR_MAX_ROWS` bulk-loss cap.

### Why bootstrap doesn't touch `conversion_drafts`

Pre-deployed runbooks are not drafts. They've already been verified by the platform or by the admin who deployed them. Threading them through the same path as case-generated drafts forced an "Activate" click in the UI for content that needed no human gate, and (the cause of multiple bug reports) created a race where freshly verified drafts could be downgraded back to "draft" by a subsequent KB-page scan.

## Path 2 — Conversion (draft → verify)

### Trigger

User uploads a document via the Dashboard. `ConversionService.convert_document()` runs the 6-stage preprocessor + LLM analysis pipeline and produces one or more `ConversionDraftModel` rows (status = `draft`).

### Algorithm (verify step)

`ConversionService.verify_draft()`:

1. Validate the draft is in `DRAFT` state and has passed validation.
2. Update frontmatter on disk (`status: draft` → `status: verified`).
3. **Attempt ingestion** via `KnowledgeService.ingest_runbook(verified_by=<user_id>, ...)`.
    - On exception → re-raise. Draft stays in `DRAFT` state. SQL row from a partial ingest (if any) was already cleaned up by `ingest_runbook` itself.
    - On `chunks_created <= 0` (now turned into an exception by `ingest_runbook`) → same handling.
4. **Only after ingestion succeeds**: set `status = VERIFIED`, `verified_at = now`, `verified_by = <user_id>`, `knowledge_item_id = <id>`. Commit.

### The bug this prevents

Prior to this design, `verify_draft` committed `status = VERIFIED` **before** attempting ingestion. If ingestion silently returned 0 chunks (BGE-M3 race during startup), the draft was left in a half-state: `status = verified` but `knowledge_item_id = NULL`.

A subsequent KBPage mount fired an auto-scan (`POST /api/v1/knowledge/scan`) that detected the half-state and "repaired" it by reverting `status` to `draft`. This was destructive: it downgraded user-verified runbooks every time the KB page was visited.

The fix is twofold:

- `verify_draft` is now atomic — status is only committed after successful ingestion.
- `_scan_for_runbooks_impl` no longer mutates half-state rows. It now logs a warning and leaves them alone (the new `verify_draft` path can no longer produce them; legacy rows surface via the log for manual admin cleanup).
- The auto-scan-on-KBPage-mount itself was removed. The Dashboard still exposes a manual "Scan for runbooks" button for operators who want it.

## Operational reset (`fm-reset-kb`)

When schema drift, embedding model changes, or accumulated bugs require a clean slate:

```bash
source .venv/bin/activate
fm-reset-kb --dry-run             # See counts; no changes
fm-reset-kb --yes                 # Wipe; bootstrap reruns on API restart
fm-reset-kb --yes --rebuild       # Wipe + immediate in-process rebuild
fm-reset-kb --yes --all-drafts    # Also delete case-generated drafts
```

Default behaviour is conservative: SQL `knowledge_items` are deleted, ChromaDB is removed, but `conversion_drafts` (which may contain case-generated work in progress) are preserved unless `--all-drafts` is passed.

The ChromaDB half is an `rmtree` of a **local** directory resolved from
`CHROMADB_KB_PERSIST_DIR`, read exactly as `create_persistent_client` reads it
— the same knob the container opens the store with, and the same one the
startup bootstrap creates it at, so the wipe and the store cannot be different
trees (fm#936). Where no local directory is the store — an external
`CHROMADB_URL` — the command refuses **before** the SQL delete instead of
leaving the two halves diverged, and it refuses likewise when the resolved path
is blank, absent, or not store-shaped; `--keep-chroma` is the explicit opt-out.
`CHROMADB_HOST` alone is *this module's* opt-in to an HTTP client and not the
container's: the client factory still returns a local `PersistentClient`, so
the reset proceeds against that tree and warns that the ingester's server-side
copy is untouched.
Operational detail:
[data-storage-management.md](../../operations/data-storage-management.md#reset--hot-rebuild).

## Invariants enforced by the code

| Invariant | Where enforced |
|-----------|----------------|
| No row in `knowledge_items` without corresponding ChromaDB chunks | `KnowledgeService.ingest_runbook` rolls back SQL on 0-chunk result |
| No draft with `status = VERIFIED` but `knowledge_item_id = NULL` | `ConversionService.verify_draft` commits status only after ingestion succeeds |
| Re-running bootstrap produces no churn for unchanged runbooks | `kb_init._ingest_pack_runbook` content-hash comparison vs the pack |
| No embedding model used to *ingest* the pack | Pack ships pre-computed vectors; `ingest_runbook(prechunked=...)` skips `model.encode` (the model still loads at boot for query-time search) |
| Pre-deployed runbooks never appear in the user's "Drafts" UI | Bootstrap writes directly to `knowledge_items`, not `conversion_drafts` |
| Half-state legacy rows are visible to operators, not silently mutated | `_scan_for_runbooks_impl` logs warning instead of reverting |

Tests covering these invariants live in `tests/unit/bootstrap/test_kb_init.py`.
