# Knowledge Base Ingestion Architecture

**Document Type:** Component Specification
**Version:** 1.0
**Last Updated:** 2026-05-26

---

## Purpose

This document specifies **how runbook content reaches the FaultMaven Knowledge Base**: the two distinct ingestion paths, the atomicity guarantees each provides, and the operational rules that prevent ingestion drift between the SQL source-of-truth and the ChromaDB vector store.

It complements:

- [`knowledge-base-architecture.md`](./knowledge-base-architecture.md) — storage and retrieval (the *what*).
- [`document-to-runbook-conversion.md`](./document-to-runbook-conversion.md) — how arbitrary documents get converted into runbook drafts.

---

## Why two ingestion paths?

A runbook can enter the KB through one of two flows. They share the **same destination tables** (`knowledge_items` + ChromaDB chunks) but originate from very different sources, and conflating them produced the bug history this design exists to prevent.

| Path | Source | Trust level | Needs human review? |
|------|--------|-------------|---------------------|
| **Bootstrap (pre-deployed)** | `data/knowledge/{scope}/**/*.md` — shipped in the repo or admin-deployed | High (platform-vetted) | No |
| **Conversion (draft → verify)** | Generated by LLM from case evidence or uploaded docs | Low until reviewed | Yes (via Dashboard "Verify" UI) |

Pre-deployed runbooks are already authored, validated, and scored before they touch disk. Forcing them through the `conversion_drafts` table — and through the per-user "Activate" UI — is ceremony without value. The conversion path exists specifically because case-generated drafts need a human gate. Bootstrap runbooks don't.

## Path 1 — Bootstrap (`faultmaven/bootstrap/kb_init.py`)

### Trigger

Runs once at API startup, immediately after the DI container has wired up `KnowledgeService`. Implementation: `bootstrap_kb()` called from `main.py` lifespan (see search for `KB Bootstrap` block).

### Algorithm

1. Eager-load BGE-M3 via `model_cache.get_bge_m3_model(triggered_by="startup")`. If the model fails to load, abort the bootstrap — there is no point attempting ingestion that will silently produce 0 chunks.
2. Walk `data/knowledge/{global,team,personal}/**/*.md`.
3. For each file:
    - Parse frontmatter (`python-frontmatter`); require `id` and `title`.
    - Derive a deterministic `item_id` = `kb_{sha256(runbook_id)[:12]}`.
    - Compare SHA-256 of file content against the existing `knowledge_items.content` row.
        - **Match** → skip; record `skipped_unchanged`.
        - **Mismatch** → delete old SQL row + ChromaDB chunks for this `item_id`, then re-ingest.
        - **No existing row** → ingest fresh.
4. Call `KnowledgeService.ingest_runbook(verified_by="system", ...)` — SQL row first, then ChromaDB embeddings.
5. If `chunks_created <= 0` or the call raised, the failure is recorded in `BootstrapResult.failed` and the next file is processed (single-file failures must not block the other 58).

### Atomicity

`ingest_runbook` now treats a 0-chunk result as a failure and rolls back its just-created SQL row (see [`knowledge_service.py: _delete_knowledge_item_row`](../../../faultmaven/modules/knowledge/domain/services/knowledge_service.py)). The combined invariant: **on any failure, no half-state remains in either store.** Callers can rely on:

- Exception raised → nothing persisted.
- Normal return → both stores updated; `chunks_created > 0`.

### Idempotency

Bootstrap is safe to re-run on every restart:

- Unchanged files are detected by content hash → no work, no churn.
- Changed files trigger explicit delete-then-ingest.
- New files are added.
- **Deleted files are NOT removed from the KB** by bootstrap — file deletion is a separate concern, owned by the Dashboard's explicit delete path. Operators who need a full reset use `scripts/reset_kb.py`.

### Why bootstrap doesn't touch `conversion_drafts`

Pre-deployed runbooks are not drafts. They've already been verified by the platform or by the admin who deployed them. Threading them through the same path as case-generated drafts forced an "Activate" click in the UI for content that needed no human gate, and (the cause of multiple bug reports) created a race where freshly verified drafts could be downgraded back to "draft" by a subsequent KB-page scan.

## Path 2 — Conversion (draft → verify)

### Trigger

User uploads a document via the Dashboard. `ConversionService.convert_document()` runs the 6-stage preprocessor + LLM analysis pipeline and produces one or more `ConversionDraftModel` rows (status = `draft`).

### Algorithm (verify step)

`ConversionService.verify_draft()`:

1. Validate the draft is in `DRAFT` state and has passed validation.
2. Update frontmatter on disk (`status: draft` → `status: verified`).
3. **Attempt ingestion** via `KnowledgeService.ingest_runbook(verified_by=<user_id>, ...)`.
    - On exception → re-raise. Draft stays in `DRAFT` state. SQL row from a partial ingest (if any) was already cleaned up by `ingest_runbook` itself.
    - On `chunks_created <= 0` (now turned into an exception by `ingest_runbook`) → same handling.
4. **Only after ingestion succeeds**: set `status = VERIFIED`, `verified_at = now`, `verified_by = <user_id>`, `knowledge_item_id = <id>`. Commit.

### The bug this prevents

Prior to this design, `verify_draft` committed `status = VERIFIED` **before** attempting ingestion. If ingestion silently returned 0 chunks (BGE-M3 race during startup), the draft was left in a half-state: `status = verified` but `knowledge_item_id = NULL`.

A subsequent KBPage mount fired an auto-scan (`POST /api/v1/knowledge/scan`) that detected the half-state and "repaired" it by reverting `status` to `draft`. This was destructive: it downgraded user-verified runbooks every time the KB page was visited.

The fix is twofold:

- `verify_draft` is now atomic — status is only committed after successful ingestion.
- `_scan_for_runbooks_impl` no longer mutates half-state rows. It now logs a warning and leaves them alone (the new `verify_draft` path can no longer produce them; legacy rows surface via the log for manual admin cleanup).
- The auto-scan-on-KBPage-mount itself was removed. The Dashboard still exposes a manual "Scan for runbooks" button for operators who want it.

## Operational reset (`scripts/reset_kb.py`)

When schema drift, embedding model changes, or accumulated bugs require a clean slate:

```bash
source .venv/bin/activate
python scripts/reset_kb.py --dry-run             # See counts; no changes
python scripts/reset_kb.py --yes                 # Wipe; bootstrap reruns on API restart
python scripts/reset_kb.py --yes --rebuild       # Wipe + immediate in-process rebuild
python scripts/reset_kb.py --yes --all-drafts    # Also delete case-generated drafts
```

Default behaviour is conservative: SQL `knowledge_items` are deleted, ChromaDB is removed, but `conversion_drafts` (which may contain case-generated work in progress) are preserved unless `--all-drafts` is passed.

## Invariants enforced by the code

| Invariant | Where enforced |
|-----------|----------------|
| No row in `knowledge_items` without corresponding ChromaDB chunks | `KnowledgeService.ingest_runbook` rolls back SQL on 0-chunk result |
| No draft with `status = VERIFIED` but `knowledge_item_id = NULL` | `ConversionService.verify_draft` commits status only after ingestion succeeds |
| Re-running bootstrap produces no churn for unchanged files | `kb_init._ingest_one` content-hash comparison |
| Pre-deployed runbooks never appear in the user's "Drafts" UI | Bootstrap writes directly to `knowledge_items`, not `conversion_drafts` |
| Half-state legacy rows are visible to operators, not silently mutated | `_scan_for_runbooks_impl` logs warning instead of reverting |

Tests covering these invariants live in `tests/unit/bootstrap/test_kb_init.py`.
