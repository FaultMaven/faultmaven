# Knowledge Base Ingestion Architecture

**Document Type:** Component Specification
**Version:** 2.0
**Last Updated:** 2026-10-29

---

## Purpose

This document specifies **how runbook content reaches the FaultMaven Knowledge Base**: the two distinct ingestion paths, the failure contract each provides, and the operational rules that prevent ingestion drift between the SQL source-of-truth and the ChromaDB vector store.

It complements:

- [`kb-pack-architecture.md`](./kb-pack-architecture.md) — the **KB pack** artifact ingested by Path 1: its format, the `KB_PACK_DIR` contract, how it's built, and how it's delivered.
- [`knowledge-base-architecture.md`](./knowledge-base-architecture.md) — storage and retrieval (the *what*).
- [`document-to-runbook-conversion.md`](./document-to-runbook-conversion.md) — how arbitrary documents get converted into runbook drafts.

---

## Why two ingestion paths?

A runbook can enter the KB through one of two flows. They share the **same destination tables** (`knowledge_items` + ChromaDB chunks) but originate from very different sources, and conflating them produced the bug history this design exists to prevent.

| Path | Source | Trust level | Needs human review? |
|------|--------|-------------|---------------------|
| **Bootstrap (pre-deployed)** | The **KB pack** (`resources/knowledge/pack`, or `KB_PACK_DIR`) — shipped runbooks + build-time vectors | High (platform-vetted) | No |
| **Conversion (draft → verify)** | Generated by LLM from case evidence or uploaded docs | Low until reviewed | Yes (via Dashboard "Verify" UI) |

Pre-deployed runbooks are already authored, validated, and scored — and embedded — by build time. Forcing them through the `conversion_drafts` table — and through the per-user "Activate" UI — is ceremony without value. The conversion path exists specifically because case-generated drafts need a human gate. Bootstrap runbooks don't.

## Path 1 — Bootstrap (`faultmaven/bootstrap/kb_init.py`)

### Trigger

Runs once at API startup, immediately after the DI container has wired up `KnowledgeService`: `_bootstrap_kb_step` in `bootstrap/lifespan.py` calls `bootstrap_kb()`. It skips under `TENANT_PROVIDER=multi`, where the `kb_seed` job seeds the pack instead, and when no KB vector store is composed (`SKIP_SERVICE_CHECKS=true`), where it logs one warning and writes nothing.

### Source: the KB pack (not the embedding model)

Bootstrap ingests the **KB pack** — a self-contained bundle of runbooks +
build-time vectors loaded via `KbPack.load(KB_PACK_DIR)`. Because every chunk
ships its **text and its vector** in the pack, **ingestion itself uses no
embedding model and no chunking** — pure SQL + ChromaDB writes. This is what turns
~tens of minutes of on-pod CPU embedding into seconds (see
[`kb-pack-architecture.md`](./kb-pack-architecture.md)). The BGE-M3 model *is*
still loaded once at boot (~5s) — from the cache **baked into the image** (CPU-only
torch, `HF_HUB_OFFLINE`/`TRANSFORMERS_OFFLINE`, so no HuggingFace fetch — works
air-gapped) — but it serves *query-time* search and the conversion/verify path; the
pre-embedded pack is ingested without it. Built-ins are not copied to `data/knowledge/` — that directory
is only the standalone import source `/knowledge/scan` reads; authored and converted drafts live in
`conversion_drafts.content`, never on disk (#1950).

### Algorithm

1. Resolve the pack directory from `KB_PACK_DIR` (default: bundled baseline at `resources/knowledge/pack`) and `KbPack.load()` it. A missing/corrupt pack logs a warning and yields an empty result — it does not crash startup.
2. For each runbook in the pack:
    - `item_id` is carried by the pack (= `kb_{sha256(runbook_id)[:12]}`).
    - Compare the pack's `content_hash` against the hash stamped on the existing `knowledge_items` row when the pack last ingested it (`metadata.pack_content_hash`) — **not** against the row's current content, which an operator may have edited (#1966).
        - **Match** → skip; record `skipped_unchanged`. Unless the row is **unserved** (#2388): complete and published, with no chunk carrying its `vector_generation` (its chunks were lost, or migration 022 gave it a generation no chunk carries). Such a row is re-ingested from the pack even though its hash matches — pre-embedded, no model, no cap — provided its stored content still hashes to the pack's `content_hash`. One an operator edited is left to the repair (step 6), which re-embeds it as it stands, so the edit is kept (#1966). Which generations the store holds is read once, id-only, before the loop.
        - **Mismatch** (a new pack version) → re-ingest, replacing the observed row by its generation (step 3). This republishes an unpublished built-in: a shipped update is a new document.
        - **No stamp** (a row ingested before the stamp existed) → an unpublished row is taken as this pack version (its retirement outranks a content edit); a published one has its content compared once. Either way a match is stamped and skipped. The stamp is written only when the pass's role may UPDATE `knowledge_items` — asked once per pass with `has_table_privilege`; the `kb_seed` maintenance role under `TENANT_PROVIDER=multi` holds no UPDATE, so there the stamp is never back-written onto an existing row (rows `kb_seed` itself ingests carry it from the INSERT; a pass whose capability check failed behaves the same way). A published row without a stamp then has its content compared on every run (exact there: a tenant cannot edit or unpublish a platform row). An older *unpublished* built-in (unpublished before the switch to multi) cannot be stamped either, so it is skipped on every run and stays unpublished across pack versions until an operator republishes it.
        - **No existing row** → ingest fresh.
3. Call `KnowledgeService.ingest_runbook(prechunked=[(text, vector), ...], verified_by=None, verification_level=COMMUNITY, replaces_generation=<the observed row's generation, or none>, ...)`. With `prechunked` supplied, the pack's chunk texts + vectors are written to ChromaDB directly — **no `ContentChunker`, no `model.encode`** — under a newly minted `vector_generation`, **before any row** (#2388). Then one transaction: a DELETE of the observed row guarded on `(item_id, vector_generation = replaces_generation)`, the INSERT of the new row complete under the new generation, at team scope the pack's own team share ensured (an idempotent add that leaves every other share of the id), and the COMMIT. Once it has committed with its guarded DELETE matched, the replaced generation's chunks are deleted (`delete_generation`, which names the parent and the generation, never the parent alone), best effort: a failure is logged and left to the generation sweep. A peer that replaced the row first makes the guarded DELETE match nothing and the INSERT conflict, which rolls the transaction back (under SQLite the loser may get `SQLITE_BUSY` instead): this ingest fails, its chunks are superseded, and the next boot decides again. No UPDATE is issued, so the `kb_seed` maintenance role's grant (INSERT and DELETE on `knowledge_items`, nothing on `resource_shares`) suffices; the shipped pack is all-global and writes no share, and a team-scoped pack entry under multi would need a grant. `verified_by` is an FK to `users.user_id` and must be a real user or `NULL` — **never a sentinel string**. Platform-shipped trust is expressed through `verification_level=COMMUNITY`, not a fake `verified_by` (a previous `verified_by="system"` violated the FK once `foreign_keys=ON` was enabled and failed every shipped-runbook ingest). Tags are coerced to strings on the way in — a bare numeric YAML tag such as `503` parses as `int`, and both the relational `KnowledgeItem` and the ChromaDB `KnowledgeBaseDocument` require `str` tags.
   The call passes `shipped=True`: a pack title is vendored, reviewed source, so it is stored as shipped. Every other caller of `ingest_runbook` leaves `shipped` at its default `False`, and the title is redacted with the sanitizer before any row or vector carries it (#1981; see [Case-Scoped PII Redaction](../security/case-scoped-pii-redaction.md) §Knowledge-Authoring Paths). A redaction outage that begins after a healthy start therefore cannot stop the platform corpus from seeding (a seed that starts with the analyzer down runs regex-only and does not raise either way).
4. If the call raised (a 0-chunk write raises before any row exists), the failure is recorded in `BootstrapResult.failed` and the next runbook is processed (single-runbook failures must not block the others).
5. **Prune orphaned built-ins.** After the loop, delete any built-in `knowledge_items` row (deterministic `kb_<12 hex>` id) not present in the current pack — typically because a runbook was removed from the pack or its frontmatter `id` changed, leaving the old deterministic row behind. The row only: its chunks then have no row, and the reconcile below collects them. Recorded in `BootstrapResult.pruned`.
6. **Reconcile the two stores + repair unserved rows** (`_reconcile_vectors` → `_repair_unserved_rows`). The prune is keyed off SQL rows, so it is structurally blind to drift where the two stores disagree. This pass compares both sides:
    - **Orphaned vectors** — a ChromaDB parent with no `knowledge_items` row. Deleted (batched), but **only its chunks older than the age floor** (`KB_INCOMPLETE_INGEST_MAX_AGE_HOURS`: a pack ingest writes its vectors before its row, #2388), and **only for built-in `kb_<12 hex>` ids** — the shared `faultmaven_kb` collection holds every tenant's vectors, and this pass does not ask whether its row read is complete (it is not under the RLS-enforced app role on PostgreSQL), so unbounded deletion could wipe other tenants. Recorded in `BootstrapResult.orphaned_vectors_cleaned`.
    - **Authored orphaned vectors** (#1982, `bootstrap/kb_orphan_sweep.py`) — an authored chunk (not a `kb_<12 hex>` parent) whose row is gone. No writer deletes vectors in-process (#2397) but the generation a known-landed switch replaced (#2388) on a row it has just committed, so a failed or cancelled authored ingest, a delete whose best-effort vector delete failed, and an update or repair that raced a delete all leave such chunks. No KB door serves them (see [Failure contract](#failure-contract)), so they are garbage, never a leak: inert, and never reused, because a retry mints a fresh `authored_item_id()`. **Report-only unless an operator arms it**, with the `storage_cleanup` gate exactly: `KB_ORPHAN_SWEEP_ENABLED` (default `false`) and `KB_ORPHAN_SWEEP_DRY_RUN` (default `true`, overridable per `kb_seed` run with `--dry-run` / `--no-dry-run`). A dry run makes every decision below and reports, per enterprise, the documents an armed run would delete; it deletes nothing. **Hard precondition for arming: one ChromaDB per database.** The `faultmaven_kb` collection is not deployment-scoped. Another database's chunks in the same collection carry stamps this database also lists (every database has the Standalone enterprise) or none, and their rows are invisible here, so their live documents read as orphans no guard below can tell apart. Measured: two databases on one ChromaDB, and database A's armed sweep deleted 10 of B's live chunks. An armed run deletes a chunk only when all of these hold:
        - it is stamped with an enterprise E from the `enterprises` table, and its parent has **no row in any enterprise**. A chunk stamped E whose parent has a row elsewhere is a mis-stamped chunk of a live document, so it is counted (`misstamped`) and kept; repair re-embeds only a document with no vectors, so it would never restore that chunk;
        - the row read is **proven complete**: SQLite, or PostgreSQL where two independent guards hold in the transaction that does the read.
            - `NOT row_security_active('knowledge_items')`.
            - The read itself runs under `SET LOCAL row_security = off`, which makes PostgreSQL *refuse* a read any policy would filter ("query would be affected by row-level security policy") instead of filtering it. This is pg_dump's mechanism, and migrations 007 and 019 use it too.

          Both hold for the table owner, a superuser and `kb_seed`'s BYPASSRLS maintenance role. They hold for no RLS-enforced role, whatever enterprise it is bound to, and not for an owner on a `FORCE ROW LEVEL SECURITY` table. Either guard alone stops a partial read, and an error from either is "unproven". `rolbypassrls` is not the test: the owner reads every row without it;
        - E passes the reference-set check (`jobs/reference_set.py`): at least one of E's authored parents has a row in E. The operator can acknowledge a disjoint E for one run, **one enterprise at a time**: `kb_seed --allow-disjoint-enterprise <enterprise_id>`, and `unattributed` names the bucket below. There is no blanket acknowledgment, and `kb_seed` refuses `--allow-disjoint-reference-set`;
        - the run deletes at most `KB_REPAIR_MAX_ROWS` documents in total, all or nothing, decided before any delete.

      **A wrongful delete is only partly healable.** Repair re-embeds a published row with no chunk of its generation, and only while the pass's unserved authored rows stay within `KB_REPAIR_MAX_ROWS` and the embedding model is available. The cap keeps one armed run's own deletes inside that bound. It does not make every wrongful delete recoverable, which is why the default is report-only.

      The chunks are listed (ids only, `where={"enterprise_id": E}`) **before** the rows are read: every AUTHORED create path commits a row before writing its vectors, so a chunk the listing saw has a row the read sees. The pack path writes its vectors first (#2388), but its ids are built-in, which this sweep never touches; so it needs no age floor. The delete is the observed chunk ids **and** E's stamp (`delete(ids=…, where={"enterprise_id": E})`), never every chunk of a parent. No database session is open across a ChromaDB call. An authored chunk whose stamp names no listed enterprise (unstamped, from before #1168, or a stamp the table does not hold — an id-only listing cannot tell the two apart) is the `unattributed` bucket, held to the same proof, check and cap.

      The counts are in `BootstrapResult.authored_orphans`, the `kb_seed` result's `authored_orphans`, and the `BootstrapResult(...)` line the CD pipeline keeps. That line carries `authored_orphans_mode` / `_would_delete` / `_deleted` / `_capped` / `_disjoint` / `_unproven` / `_misstamped` / `_unremoved`. A delete that raised is `unremoved`, because the CD gate reads the line's last `failed=`. The counts cover what an unproven read, a disjoint enterprise, the cap or a failed delete leaves. Built-ins are never touched by the sweep.
    - **Incomplete ingests** (#2394, `bootstrap/kb_incomplete_sweep.py`) — a row an authored ingest left with `ingest_complete` false (see [Failure contract](#failure-contract)), older than `KB_INCOMPLETE_INGEST_MAX_AGE_HOURS` (default 24; a younger one may be an ingest still running). Removed with its vectors, in this order: the row's DELETE, guarded on its stamp and on `ingest_complete` false, uncommitted; one vector delete by parent id; commit. This sweep is a collector, not a writer, so it keeps the row until its vectors are gone: a failed vector delete rolls the row back for the next run, and a row whose guarded delete matches nothing (it completed or went since the read) is counted `spared`. It is the first step of every `bootstrap_kb`, before `KbPack.load`, so a pack that does not load does not skip it. The web startup deletes; `kb_seed` is report-only until armed, with the authored-orphan sweep's gate (`KB_INCOMPLETE_INGEST_SWEEP_ENABLED`, default `false`; `KB_INCOMPLETE_INGEST_SWEEP_DRY_RUN`, default `true`; `--dry-run` / `--no-dry-run`). Counts: `BootstrapResult.incomplete_ingests`, the `incomplete_ingests_*` keys on the `BootstrapResult(...)` line (`_mode`, `_would_delete`, `_deleted`, `_unremoved`, `_spared`, and `_skipped`: `disabled`, `no_vector_store` or `error` when it did not run), and the `kb_seed` result's `incomplete_ingests`. The bound affects only liveness: an ingest whose row was swept fails its guarded completion and raises, and the vectors it wrote stay under an id no row admits. The reconcile below keeps an incomplete row in its row set, so its vectors are never orphans, and out of both the repair set and the unpublished set, so it neither re-embeds the row nor deletes an in-flight ingest's vectors.
    - **Unpublished built-ins with vectors** — a built-in parent whose row exists but is unpublished (#1966). Deleted in the same batch (same built-in-only boundary, same age floor: a re-ingest of a new pack version writes its vectors before it replaces the row). Every unpublish leaves them: `delete_document` unpublishes a built-in with a SQL-only flip and no vector call (#2397). No KB door serves them meanwhile; this pass is what collects them. Recorded separately in `BootstrapResult.unpublished_vectors_cleaned`.
    - **Superseded generations** (#2388, `bootstrap/kb_generation_sweep.py`) — a chunk whose parent has a complete row this pass reads, and whose id names no generation (written before #2388) or another generation than the row's. No door serves them. The writer that switched the row deletes the generation it replaced once its commit has landed (step 3 and the content update below), so what this sweep collects is the rest: a writer's delete that failed, the generation a racing update overwrote, a failed write's chunks, and every chunk written before #2388. Deleted once older than the age floor (`KB_INCOMPLETE_INGEST_MAX_AGE_HOURS`; the young ids come from one filtered, id-only read, `indexed_at >= cutoff`, and ChromaDB's `$gte` skips a chunk without the key, so every other listed id is old or pre-#2388), by the observed ids, a page at a time. A row-less parent is left to the reconcile and the authored-orphan sweep, an incomplete row's to the incomplete-ingest sweep; the served generation is never touched, so there is **no document cap**. Its one false positive is a second database on the same ChromaDB, which holds the same built-in ids under other generations: **one ChromaDB per database** is its precondition, as for the authored-orphan sweep. Gate, its own: the standalone web startup deletes only when the store is a local `PersistentClient` and is report-only under an external `CHROMADB_URL`; `kb_seed` is report-only unless armed (`KB_GENERATION_SWEEP_ENABLED`, default `false`; `KB_GENERATION_SWEEP_DRY_RUN`, default `true`; `--dry-run` / `--no-dry-run`). Arming the incomplete-ingest sweep does not arm it. So under `TENANT_PROVIDER=multi` or an external `CHROMADB_URL`, a writer's own delete is what collects superseded chunks until an operator arms the sweep, and the pre-#2388 chunks stay (never served) until then or until a re-provision. It runs right after the incomplete-ingest sweep, before `KbPack.load`. Counts: `BootstrapResult.generation_sweep`, the `generation_sweep_mode` / `_would_delete` / `_deleted` / `_unremoved` / `_skipped` keys on the `BootstrapResult(...)` line (chunks), and the `kb_seed` result's `generation_sweep`.
    - **Unserved rows** — a **published, complete** `knowledge_items` row no chunk of whose `vector_generation` exists (by the generations the chunk ids name, #2388): a row whose vectors were lost after its ingest completed (a wiped collection), or one migration 022 gave a generation no chunk carries; silently non-retrievable. An unedited pack row is re-ingested from the pack at step 2; what is still unserved after it — an authored row, a built-in an operator edited, or a built-in whose re-ingest failed — goes to the repair. **Order:** the rows are read before the chunks are listed, and each candidate's generation is read again after the listing; a row whose generation changed between the reads (an update that committed and deleted the generation it replaced) is not reported. A row inserted or replaced between the reads wrote its vectors first, so they are younger than the age floor, which keeps the reconcile's two deletes from touching them. An authored row a failed ingest leaves is never one: it is incomplete until its vectors exist, and the sweep above owns it (#2394). An unpublished row is never unserved: it is retired, no KB door serves its chunks, and re-embedding it would only write vectors nothing serves (#1966); `reindex_missing_vectors` also refuses one. A **bounded** repair re-chunks + re-embeds the row's persisted `content` with BGE-M3 and writes only the vector store (`KnowledgeService.reindex_missing_vectors`) — the SQL row, the source of truth, is never touched. A delete or unpublish that lands during the embed leaves the repair's vectors under a row no KB door admits: they are never served, and never discarded in-process (#2397); an authored document's are removed only by the authored-orphan sweep once an operator arms it. The repair writes under the row's own generation, read in the same SELECT as its content; a re-run under the same generation is idempotent with no delete (ChromaDB's `add` keeps the chunk already stored under an id, measured on 1.5.8). Repaired ids → `BootstrapResult.repaired_rows`; the rows still unserved — those the repair could not do (embedding model unavailable, ChromaDB error, past the cap) — are `BootstrapResult.unserved_rows` (and the `kb_seed` result's `unserved_rows`): the number of complete rows this deployment serves nothing for, re-attempted next boot. Repair only **adds** a row's own vectors, so — unlike the delete side — it is cross-tenant-safe. It is bounded twice: `KB_REPAIR_MAX_ROWS` (25) treats a larger set as a bulk-loss anomaly (e.g. the vector collection was wiped) and repairs nothing (recovery there is re-provisioning: `fm-reset-kb` on standalone, the deployment wipe under multi); `KB_REPAIR_MAX_CHUNKS` (60) caps the embedding **work** per boot, since this repair runs on the lifespan startup path *before the app serves readiness* and the timeout risk is chunk count × pod CPU, not row count — rows past the budget defer to the next boot (per-row vectors persist, so repair is incremental). This is the one bootstrap step that **loads the embedding model**, and only when there is at least one unserved row the pack did not re-ingest, so the fast model-free boot is preserved in the common case.

      > **Ops note.** Both bounds are configurable per deployment via `KB_REPAIR_MAX_ROWS` / `KB_REPAIR_MAX_CHUNKS` (env → `DatabaseSettings`; defaults 25 / 60 in `faultmaven/bootstrap/kb_init.py`). Which path runs the repair depends on the tenancy provider, **not** on cloud-vs-self-hosted (both run the same unified codebase and can be multi-tenant): under a single-tenant `TENANT_PROVIDER` the web-startup bootstrap runs the repair on the lifespan critical path *before readiness*, so a repair of up to `KB_REPAIR_MAX_CHUNKS` chunks (plus the model load) delays startup — lower the budget (or widen a tight k8s `startupProbe`) if needed. Under `TENANT_PROVIDER=multi` the web bootstrap is skipped entirely and repair runs in the `kb_seed` maintenance job, off the readiness path.

### Failure contract

Two stores cannot commit together, and no read needs them to (#2397). **Every KB read door admits a chunk only when its parent has a complete, published `knowledge_items` row at query time, and the chunk carries that row's `vector_generation`** (#2388): the investigation pre-fetch (push), `POST /knowledge/search` (`search_documents`), the `kb_qa` pull and runbook dedup. The check is the knowledge module's `IKnowledgeService.admitted_generations`, one SELECT of `(item_id, vector_generation)` where `ingest_complete AND is_published`, with no caller identity; a door keeps a hit only when its `metadata.vector_generation` is a non-empty string equal to its parent's (`admission.chunk_admitted`), so a chunk with no generation is never admitted. Every row INSERT and every content change mints a generation (32 hex digits); every chunk id is `{item_id}_chunk_{i}_{generation}`, and its metadata carries `vector_generation` and `indexed_at`. The stores only apply it, as an `admit` callback the knowledge module hands them: `hybrid_search` before its top-k cut, `search` after its recall, and `RunbookKnowledgeBase` (built with it) between its query and its parse. A full page admission thinned short (an unpublished built-in's chunks can fill a window until the reconcile removes them) is read again with its fetch doubled, up to 8× (`read_deepening`); if dedup's deepest page still kept no published runbook it raises `RUNBOOK_SEARCH_INCOMPLETE`, so core takes its "could not check" caveat. A store refuses a read without a callable check (`TypeError`). A chunk's parent is named by one rule: `metadata.parent_document_id`, else the id before its last `_chunk_`. When the check cannot run it raises `KnowledgeBaseError` (`KNOWLEDGE_ADMISSION_UNAVAILABLE`), never an empty set, and each door fails as it does on a store error: the push carries on without KB, `search_documents` answers its "unavailable" body, the pull returns a tool failure (#943), dedup raises (#944).

So **no ingest, repair or prune deletes a vector on any failure path, and no writer deletes by parent to replace**: a vector delete racing a write still in flight, or one whose outcome is unknown, is what #2397 and #2063 were, and a delete by parent removed a concurrent writer's chunks, which is what #2388 was. The one writer delete is exact and comes after a known-landed commit (ruling (i) on #2388): the writer that switches a row's generation — a content update, a pack replacement — then deletes that parent's chunks of the generation it replaced (`delete_generation`), best effort, and never on a failed or in-doubt commit. Generations are never reused, so no row serves those chunks again. Every other vector delete is a collector's (step 6), on chunks older than the age floor or whose row is gone or incomplete, plus `delete_document`'s best-effort one after its row DELETE.

- **Authored ingest** (every caller but the pack bootstrap): the row first, inserted with `ingest_complete` false under a new generation, then its vectors under it; once they are written, ONE transaction completes the row and records its caller (#2394, #2396): an UPDATE setting it true, matching only the id's row that carries this call's `created_at` stamp and is still incomplete; at team scope, the team share (`resource_shares`) through a share repository bound to that session, which never commits; then the caller's `record` (`verify_draft`'s compare-and-swap of its draft, `upload_document`'s upload, job and draft rows); then one COMMIT. **An authored runbook is ready only in the commit that records its caller's success**, and a caller told "failed" is never left with a ready item. A flip matching no row, a `record` that returns False (`IngestNotRecorded`) or raises, rolls the whole transaction back. Any failure from the INSERT on — the row's commit landing and then raising, the vector write raising, timing out or yielding 0 chunks, the completing transaction, or a cancellation — runs one SQL-only cleanup ([`knowledge_service.py: _delete_knowledge_item_row`](../../../faultmaven/modules/knowledge/domain/services/knowledge_service.py), #2365, #2378): it deletes the row carrying this call's stamp **only while it is incomplete**, so it never deletes a completed row, and no share, since an incomplete row has none. It never touches the vectors. A failure before the completing COMMIT is issued (the flip, the share, `record`, a session that never opened, or anything earlier) made nothing ready, and is re-raised as itself, whatever the cleanup found. A failure from that COMMIT on (the COMMIT, or its session's exit after it) is decided by that DELETE, which waits for the transaction's lock (the row's on PostgreSQL, the writer lock on SQLite) and is its session's first statement; the read of the row follows it, since a read does not wait for a writer and would see the row as it stood before that transaction:

  | The guarded DELETE | Then | The caller gets |
  |---|---|---|
  | matched the row | the COMMIT did not land | the original error |
  | matched nothing; the row under this stamp is complete | the COMMIT landed, with the caller's record | the success (for a cancellation: the cancellation) |
  | matched nothing; no such row | | the original error |
  | raised (or the read after it did) | the row is complete with the caller's record, or incomplete, never served, and left for the incomplete-ingest sweep where it is armed | `IngestOutcomeUnknown`: HTTP 500, `x-error-code: KB_INGEST_OUTCOME_UNKNOWN`, no `Retry-After`, "The runbook may have been published. Retry with the same Idempotency-Key to learn whether it was; without a key, check the knowledge base before retrying."; `verify-batch` reports the draft `unknown` |

  A cancellation is always re-raised as it arrived, and so, while the task is being cancelled (`cancelling() > 0`), is a failure carrying a `CancelledError` on its `__cause__` or `__context__` chain (a close that raised while the cancellation propagated); a `TimeoutError` from `asyncio.timeout()` or `wait_for()` chains one with no cancellation pending, and is an exception; the DELETE still runs, shielded. A 503 is not used: in this API it says nothing was saved, and a client honouring its `Retry-After` would publish an upload twice.
- **Pack ingest**: the vectors first, then the one row transaction of step 3. A failure writes no row, or leaves the row it would have replaced as it was. **Residual:** two live replicas on different pack versions alternate the row at each other's boots; only the surviving row's generation is served; each alternation's winner deletes the generation it replaced, and the loser's chunks are left for the sweep. That is what #2388 reduces to.
- **Content update** (`update_document_metadata`): the new chunks under a new generation first, then ONE UPDATE writing the content and that generation together. A failed UPDATE leaves the old content served; one that raised but landed serves the new; of two racing updates, whichever lands last leaves the content and the generation of the same call. Once the UPDATE has returned committed, the generation it replaced is deleted, best effort; a failed or in-doubt commit deletes nothing.

What a failed ingest leaves, and what collects it:

- **Vectors no row admits** — whatever the indexer wrote, including an `add_documents` that lands after the cancel (the HTTP ChromaDB client runs it on `CHROMA_EXECUTOR`, and a cancellation ends the await, not the thread). Their generation is no row's, so they are never served. A built-in id's are collected by the generation sweep (a row stands) or the reconcile (none does), once older than the age floor. An authored id's are collected only by the authored-orphan sweep, which is report-only unless an operator arms it; under `TENANT_PROVIDER=multi` nothing collects by default (the web lifespan skips `bootstrap_kb`, and `kb_seed`'s sweeps are report-only). Until then they are inert.
- **A row the authored cleanup could not remove** (its delete raised, or waited on a lock past its bound). After a failure before the completing COMMIT, it never completed, so it stays incomplete — never served or listed, and swept with its vectors once stale where the sweep is armed. After a failure of that COMMIT, it is incomplete in the same way, or complete with its caller's record: the `IngestOutcomeUnknown` case of the table above (#2396). The cleanup never deletes a completed row.

The full list, with the predicates that decide each case (an INSERT whose COMMIT is in doubt, another call's row under the id), is in `ingest_runbook`'s docstring. **Why the completion, and not the INSERT, decides:** `_complete_authored_ingest`'s docstring states which commit decides the completion, the lock each dialect holds until that commit, and how long the cleanup's `created_at`-guarded delete waits on it. The cleanup is shielded from an anyio scope's cancellation (`anyio.CancelScope(shield=True)`), because under `BaseHTTPMiddleware` a cancelled request's anyio scope cancels every unshielded await. It is best effort: a step that fails is logged. Callers can rely on:

- Exception raised (authored, from `create` on) → `_delete_knowledge_item_row` ran first, and nothing the call wrote is ready, but after `IngestOutcomeUnknown`, raised when the completing COMMIT's outcome could not be learned; (pack) the row transaction did not commit. Either way nothing the call wrote is served, but for that and the residuals above.
- Normal return → both stores updated, the caller's `record` committed with the row's completion; `chunks_created > 0`.

**A delete is SQL-first.** `delete_document` commits the row change — an authored document's `DELETE` (with the drafts naming it discarded, #2369), or a built-in's `is_published = false` — and then, for an authored document only, deletes its vectors best effort, outside any transaction. A failure there, a timeout included, is logged and not raised: from the commit on, no door serves the document, so the route's 204 means no chunk of it is retrievable through a KB door (an excerpt already in a case's prompt stays until that case's next fetch). An unpublish makes no vector call; the next pack-loading bootstrap's reconcile removes its vectors. An update or repair that finds its row gone or unpublished writes no vector delete either.

`KnowledgeService.upload_document` writes its `uploaded_files`, `conversion_jobs` and verified `conversion_drafts` rows as the `record` of `ingest_runbook`, in the transaction that completes the item: after the item's row exists, because the draft's `knowledge_item_id` is a foreign key to it, and in its completing commit, so the upload is the item with its rows or neither (#2396). Nothing withdraws an item on a caller's failure: there is no commit after the item's to fail.

**Keyed uploads and conversions (#2433).** A `POST /knowledge/documents` or `POST /knowledge/convert` with an `Idempotency-Key` writes a `kb_request_receipts` row in the transaction that publishes: the upload's in that `record`, a conversion's in `_persist_job_rows`, with the job and its team share. So the receipt exists exactly when the request published, and it is deleted with its item or job. The route (`modules/knowledge/api/request_idempotency.py`) takes an owner-tokened claim (`kb-inflight:…`, a lease renewed while the request runs), then looks the receipt up: the same file and fields replay its 201, another file or field is 409 `IDEMPOTENCY_KEY_REUSE`, a held claim is 409 `KB_REQUEST_IN_PROGRESS`. After `IngestOutcomeUnknown` the retry under the key replays if the COMMIT landed and runs if it did not. A duplicate that ran without a claim is refused at the receipt's key in its own transaction (`KbReceiptExistsError`, classified after the session closes), so the cleanup has already removed its incomplete row, and the route answers it with the first's receipt.

### Idempotency

Bootstrap is safe to re-run on every restart:

- Unchanged runbooks are detected by the pack hash stamped on the row at ingest → no work, no churn, and an operator's edit of a shipped runbook is never mistaken for a pack change.
- A new pack version of a runbook is re-ingested: its vectors under a new generation, then one transaction replacing the observed row by its generation. Once that commits, the replaced generation's chunks are deleted, best effort. The generation sweep is the backstop for a delete that failed and for chunks written before #2388: armed on a standalone local store, report-only elsewhere until an operator arms it.
- New runbooks are added.
- **Built-ins are pack-reconciled (add / skip / prune).** A built-in row (`kb_<12 hex>` id) not present in the current pack — because the runbook was removed or its `id` changed, orphaning the old deterministic id — is pruned at the end of bootstrap (step 5). **The pack is the source of truth for built-in content.**
- **Authored/user content is never auto-removed.** Items created by `verify_draft` or the API carry random-UUID ids, which the `kb_<12 hex>` prune pattern cannot match — so the prune is structurally incapable of touching them. Removing those is the Dashboard's explicit delete path. Operators who need a full reset use `fm-reset-kb`. The authored-orphan sweep (step 6) deletes only **vectors** whose row is already gone, never a row. The incomplete-ingest sweep (step 6) deletes only a row whose ingest never completed, which no reader lists (#2394).
- **Safety guard:** if the pack yields zero runbook ids (a load/parse anomaly, not a legitimate "remove everything"), the prune is skipped entirely.
- **Self-healing across stores.** A complete row no chunk of its generation serves is re-ingested from the pack (an unedited built-in, step 2) or re-embedded as it stands (an authored row or an edited built-in, step 6) on the next boot, so it does not stay silently unretrievable — the latter subject to the `KB_REPAIR_MAX_ROWS` bulk-loss cap; what is left is counted as `unserved_rows`. An authored row whose ingest died is incomplete and is swept instead, never published by the repair (#2394).

### Why bootstrap doesn't touch `conversion_drafts`

Pre-deployed runbooks are not drafts. They've already been verified by the platform or by the admin who deployed them. Threading them through the same path as case-generated drafts forced an "Activate" click in the UI for content that needed no human gate, and (the cause of multiple bug reports) created a race where freshly verified drafts could be downgraded back to "draft" by a subsequent KB-page scan.

## Path 2 — Conversion (draft → verify)

### Trigger

User uploads a document via the Dashboard. `ConversionService.convert_document()` runs the 6-stage preprocessor + LLM analysis pipeline and produces one or more `ConversionDraftModel` rows (status = `draft`).

### Algorithm (verify step)

`ConversionService.verify_draft()`:

1. Validate the draft is in `DRAFT` state and has passed validation.
2. Update frontmatter on disk (`status: draft` → `status: verified`).
3. **Ingest** via `KnowledgeService.ingest_runbook(verified_by=<user_id>, record=<the swap>, ...)`. The title is redacted here, and the draft row's own title is rewritten to match (#1981), so a draft that predates the scrub is not left listed with its raw title after publication.
4. **The swap is the ingest's `record`** (#2396): in the transaction that completes the item, a compare-and-swap sets `status = VERIFIED`, `verified_at`, `verified_by = <user_id>`, `knowledge_item_id = <id>` and the verified text, only while the draft is still `DRAFT` holding exactly the text that was read. One commit makes both the item ready and the draft verified.
    - The swap misses (another verify, a delete, or an edit won) → `IngestNotRecorded`: nothing is published, and the caller gets a 409 naming what won.
    - Any other failure → re-raise. Draft stays in `DRAFT` state, and nothing a KB door serves is left; an outcome that cannot be learned is `IngestOutcomeUnknown`. See [Failure contract](#failure-contract).

### The bug this prevents

Prior to this design, `verify_draft` committed `status = VERIFIED` **before** attempting ingestion. If ingestion silently returned 0 chunks (BGE-M3 race during startup), the draft was left in a half-state: `status = verified` but `knowledge_item_id = NULL`.

A subsequent KBPage mount fired an auto-scan (`POST /api/v1/knowledge/scan`) that detected the half-state and "repaired" it by reverting `status` to `draft`. This was destructive: it downgraded user-verified runbooks every time the KB page was visited.

The fix is twofold:

- `verify_draft` commits `status = VERIFIED` only in the commit that completes the ingestion (#2396); a failed ingestion leaves the draft a draft, and the item to the [failure contract](#failure-contract).
- `_scan_for_runbooks_impl` no longer mutates half-state rows. It now logs a warning and leaves them alone (the new `verify_draft` path can no longer produce them; legacy rows surface via the log for manual admin cleanup).
- The auto-scan-on-KBPage-mount itself was removed. The Dashboard still exposes a manual "Scan for runbooks" button for operators who want it.

## Operational reset (`fm-reset-kb`)

When schema drift, embedding model changes, or accumulated bugs require a clean slate:

```bash
source .venv/bin/activate
fm-reset-kb --dry-run             # See counts; no changes
fm-reset-kb --yes                 # Wipe; bootstrap reruns on API restart
fm-reset-kb --yes --rebuild       # Wipe + immediate in-process rebuild
fm-reset-kb --yes --all-drafts    # Also delete every draft (upload, document, case)
```

Default behaviour is conservative: SQL `knowledge_items` are deleted, ChromaDB is removed, but `conversion_drafts` are preserved unless `--all-drafts` is passed. A draft that published a deleted runbook is discarded first, its text kept, so it is not left listed as verified (#2369). `--all-drafts` deletes every draft instead (upload, document and case drafts alike; for an authored runbook whose item the reset deletes, its draft holds the last copy of its text). On either path the reset then releases each case key held by a conversion job with no live draft left, so that case can be converted again (#2387). Only the items the reset locked are deleted; one a running API writes meanwhile is kept and reported.

The ChromaDB half is an `rmtree` of a **local** directory resolved from
`CHROMADB_KB_PERSIST_DIR`, read exactly as `create_persistent_client` reads it
— the same knob the container opens the store with, and the same one the
startup bootstrap creates it at, so the wipe and the store cannot be different
trees (fm#936). Where no local directory is the store — an external
`CHROMADB_URL` — the command refuses **before** the SQL delete instead of
leaving the two halves diverged, and it refuses likewise when the resolved path
is blank, absent, or not store-shaped; `--keep-chroma` is the explicit opt-out.
Operational detail:
[data-storage-management.md](../../operations/data-storage-management.md#reset--hot-rebuild).

## Invariants enforced by the code

| Invariant | Where enforced |
|-----------|----------------|
| No draft with `status = VERIFIED` but `knowledge_item_id = NULL` | `ConversionService.verify_draft` commits status only in the commit that completes the ingestion; `KnowledgeService.delete_document` and `fm-reset-kb` discard the drafts naming an item before deleting it (`draft_retirement`, #2369). Another deleter can still leave one (the key's `SET NULL`; #2385) |
| An authored row is complete only in the transaction that records its caller | `KnowledgeService._complete_authored_ingest` runs the flip, the team share and the caller's `record` in one transaction with one COMMIT; `_delete_knowledge_item_row` deletes only an incomplete row (#2396) |
| Re-running bootstrap produces no churn for unchanged runbooks | `kb_init._ingest_pack_runbook` compares the pack's hash with `metadata.pack_content_hash` stamped at ingest, and re-ingests a matching row only when no chunk carries its generation |
| A chunk is served only under its row's generation; no writer deletes a vector but the generation its known-landed commit replaced | `IKnowledgeService.admitted_generations` + `admission.chunk_admitted` at every door; `_index_document_in_vector_store` deletes nothing, and `KnowledgeService._delete_replaced_generation` runs only after a committed switch (#2388) |
| No embedding model used to *ingest* the pack | Pack ships pre-computed vectors; `ingest_runbook(prechunked=...)` skips `model.encode` (the model still loads at boot for query-time search) |
| Pre-deployed runbooks never appear in the user's "Drafts" UI | Bootstrap writes directly to `knowledge_items`, not `conversion_drafts` |
| Half-state legacy rows are visible to operators, not silently mutated | `_scan_for_runbooks_impl` logs warning instead of reverting |

Tests covering these invariants live in `tests/unit/bootstrap/test_kb_init.py`.
