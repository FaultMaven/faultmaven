## Context — what this system is (for a reviewer new to it)

**FaultMaven** is an AI troubleshooting copilot: an investigation engine that works an incident the way a seasoned engineer does — goal-driven, evidence-based — and learns from resolved cases. Two subsystems meet in this plan.

**The investigation engine** (`faultmaven/core/investigation/`). Each case builds a **causal graph**: `CausalNode`s typed `root → intermediate → problem`, wired by `CausalEdge`s into cause→effect chains terminating at the problem node `D`. A **`Hypothesis`** heads a chain (`root_node_id` + `path`). Hypotheses carry a likelihood, **decay** when stagnant (`0.85^iterations`), are flagged by **anchoring detection**, and reach **VALIDATED** only through evidence-driven state derivation (node VALIDATED is written by `derive_node_states` (empirical) and `validate_by_exclusion` (deductive, the #593 exclusion arm); hypothesis VALIDATED is projected from node states by `project_hypothesis_states_from_roots` — these are the *sole* VALIDATED writers). The engine is bound by **two hard guarantees**: **NO INCORRECT CONCLUSION** and **NO COLLAPSE UNDER PRESSURE** (it must not be led into a wrong root cause). Every design choice here is measured against those two.

**The knowledge base** (`faultmaven/modules/knowledge/` + the sibling `faultmaven-kb-toolkit` repo). Runbooks are authored in a **v4 causal-chain template** whose per-Cause structure (`chain_nodes` / `chain_edges` / `rung_indicators` / `interventions`) deliberately mirrors the engine's own causal-graph shape. A build step (`pack_builder._extract_causes`) compiles runbooks + pre-computed BGE-M3 vectors into a **KB pack**; bootstrap ingests it into `knowledge_items` (+ ChromaDB). At runtime the engine retrieves runbooks via hybrid vector+BM25 search.

The system runs in **two directions**: *consume* (runbook → investigation) and *produce* (resolved case / uploaded doc → new v4 runbook → back into the KB — the **knowledge flywheel**). This plan came out of a **full-pipeline KB review (2026-07-15)** — template → pack → ingest → RAG → engine → flywheel — which found the producer half cohesive but the **consumption boundary broken**.

## The problem & objectives

**Core problem — the structured causal record was write-only.** Template, pack builder, and engine all speak the same causal shape, and every runbook ships a full `metadata["causes"]` graph record that ingestion persists — **but nothing read it at runtime.** The engine consumed KB only as **flat RAG prose**: `answer_from_kb` synthesized chunks → prose, then the engine LLM re-parsed the `### Cause` markdown and flattened it to **one** `hypotheses_to_add` (a ≤800-char description). A **double-collapse** (summary of a summary) that threw away the runbook's machine-readable causal structure exactly where the engine could use it most.

Secondary problems the review found (each mapped to a phase below): dead/inert retrieval subsystems; case domain/service never wired into KB ranking; a relay-vs-synthesis prompt tension compressing runbook steps before the engine sees them; a duplicated runbook-conversion readiness gate (**#698**); ingestion/vector robustness gaps; kb-toolkit hygiene drift.

**Objective.** Make the KB's structural investment pay off end-to-end — the engine consumes runbook causal structure *as structure* (candidates in the graph), and case-generated runbooks re-enter *as structure* (flywheel symmetry) — **without weakening either guarantee.** A runbook is a **prior, not a gate**: it may seed candidate hypotheses to *test*, never grant a conclusion. This is explicitly **not** the retired runbook-cause *matcher* (a deterministic grounding gate, NO-GO'd in #658); **seeding ≠ gating**.

**Success criteria.** (1) Structured `causes` has a runtime consumer; the double-collapse is gone for matched runbooks. (2) Both guarantees provably hold under a seeded prior — mechanical, LLM-agnostic eval including a *misleading-runbook* scenario. (3) The flywheel is symmetric — a converted runbook re-enters as structured candidates, not just prose. (4) No drift-prone dead code or duplicated gates left behind.

## The decision that shapes this plan — DECIDED 2026-07-15: Option B (build the seeder)

The runbook template, pack builder, and engine causal-graph models all speak the **same** structured shape, and every runbook ships a full `causes` graph record that ingestion persists to `knowledge_items.metadata["causes"]` — but **nothing reads it at runtime**. The engine consumes KB only as flat RAG prose. Two coherent resolutions:

- **Option B (recommended) — build the deterministic seeder.** Read `metadata["causes"]` for retrieved runbooks and instantiate `CausalNode`/`CausalEdge`/`Hypothesis` **candidates** directly in the case graph (prior, not gate; never VALIDATED without case evidence; a failed fix demotes). This makes the structure investment pay off and removes the lossy double-synthesis. It is **not** the retired matcher (that was a deterministic *gate*; this is *seeding*).
- **Option A — commit to RAG-only.** Stop extracting/shipping/persisting the `causes` record and retire its cross-repo CI; document runbooks as RAG-only. Smaller, removes a drift-prone triple grammar, but permanently forgoes structural cohesion.

**Option B is chosen** (build the seeder). Phase 4 is the centerpiece. The "If Option A" variant under Phase 4 is retained only as the recorded rejected alternative; it is **not** the path being executed.

## Phase 4 — Centerpiece: KB → engine structural cohesion *(requires Phase 1 = B)* — ✅ **MERGED (PR #712, flag OFF)** · 4.6b enabling eval RUN + PASSED on BEST_EFFORT (fireworks); cross-provider retries optional

**Why here:** ground is clean (P2), retrieval is better (P3), and this is the change that makes the whole pipeline's structure pay off. **Design-doc-with-implementation: design first, same PR.**

- **4.1 Design.** Add an ADR / section: the **KB cause seeder** reads `knowledge_items.metadata["causes"]` for a retrieved runbook and instantiates its Cause chain as **CANDIDATE** `CausalNode`s (`root`/`intermediate`/`problem`) + `CausalEdge`s (seeded chains are OR-alternatives; `and_group` AND-convergence is **assert-and-reject until first real use** — see 4.8, and the boundary note below) + a `Hypothesis` header (`root_node_id` + `path`). Invariants: candidate-only (never VALIDATED without case evidence), engine-derived `cause_state`, failed-fix demotes, single-root-per-Cause, sibling MECE (M1–M7). Explicitly distinguish from the retired **matcher/gate** (`project_runbook_matcher_nogo`): this is a *prior*, not a gate.
  - **Anchoring/decay invariant (guarantee-critical).** A seeded chain is a strong prior that can *anchor* the LLM toward a wrong theory it then rationalizes — the NO-COLLAPSE-UNDER-PRESSURE failure mode. Seeded candidates MUST be subject to the **same confidence decay (`0.85^iterations`) and anchoring detection** the engine applies to normal hypotheses — not merely failed-fix demotion. An unsupported seeded prior must decay and be flagged by anchoring detection exactly like a self-generated one; seeding grants no evidentiary privilege.
  - **Scope boundaries / limitations (state explicitly; don't overclaim coverage).**
    - **`and_group` AND-convergence is not modeled — assert-and-reject. [IMPLEMENTED `2ca0aa9d`.]** The seeder reads `chain_edges` as `cause_ref`→`effect_ref` only and enters every predecessor as an OR-alternative; it does **not** honor `and_group` (0 instances in today's corpus). Fully modeling AND now would be speculative code for a zero-instance shape (the plan's own no-speculative-shapes rule). So the seeder **skips-and-logs** any cause whose `chain_edges`/`chain_nodes` carry a non-null `and_group` (`unsupported_shape` skip class, see 4.8) rather than silently flatten AND→OR (a MECE mis-model). The guard exists for **Phase 5's produce path** — produce/consume symmetry means a converted runbook could author the first AND-convergence. Real AND-modeling is deferred until that first instance.
    - **One-shot seeding boundary. [DOCUMENTED + MEASURED — design doc "Boundary" section, `183f17e3`.]** Seeding fires **once**, at the INQUIRY→INVESTIGATING transition, keyed on the *confirmed* problem statement (`case.description = inquiry.proposed_problem_statement`), so **all INQUIRY-phase symptom scoping is captured**. The residual gap is narrow: a runbook findable **only from evidence gathered after** symptom-verification (mid-INVESTIGATING discovery) is never seeded — it falls back to flat-prose consumption. This is a *deliberate* boundary (re-seeding mid-investigation has a real re-anchoring cost against NO-COLLAPSE), **not** an oversight — no default re-seed hook. **Measured (flag-ON, fireworks):** a vague case narrowed *during INQUIRY* still seeds the correct runbook, so the residual is confined to post-verification discovery; verdict = a guarded re-seed (natural site: the existing `"root_cause"` refetch at `milestone_engine.py:8251`) is **not urgent**. Revisit only if a later eval shows the residual materially hurts outcomes.
- **4.2 Surface source identity in retrieval.** Chunk metadata already carries `parent_document_id`/`document_id`; ensure the retrieval result exposes the matched runbook id(s) so the seeder can load that runbook's `causes` record from `knowledge_items`.
- **4.3 Implement the seeder in the engine** (milestone turn flow): when KB retrieval surfaces a runbook whose Cause Indicators align with current evidence, seed that Cause's chain as candidates. Keep the LLM-mediated path as fallback for prose-only sources (converted drafts that lack a `causes` record).
  - **Multi-runbook merge rule (required).** Retrieval routinely returns several runbooks; two roots from different runbooks can violate single-root-per-Cause / sibling-MECE across the *merged* case graph (M1–M7 govern one Cause, not the merge). Define the rule explicitly: (a) **cap** what is seeded (e.g. top-N runbooks by rerank score, N small); (b) roots from distinct runbooks enter as **competing OR-alternative sibling causes**, never merged into one Cause; (c) **dedup** by cause identity (statement/root equivalence) so the same cause retrieved via two runbooks seeds once; (d) preserve sibling-MECE — if two seeded roots are not discriminable, keep both as candidates and let evidence separate them (do not silently collapse). State this in the ADR and test it.
- **4.4 Prompt alignment.** Update the `KNOWLEDGE & RUNBOOK AUTHORITY` block so that when structured candidates are already seeded, the LLM **validates/refutes against evidence** rather than re-deriving structure from prose — eliminating the double-collapse (kb_qa synthesis → engine re-summary).
- **4.5 Close the causes-freshness gap** (now real): the content-hash idempotency gate must detect `causes` changes (fold `causes` into the hash, or re-extract on every ingest) so the live consumer never reads stale structured data.
- **4.6 LLM-agnostic eval.** Pass/fail is **mechanical engine-state assertions** (given a known runbook + matching evidence, the graph is seeded with the expected nodes/edges/root; a *wrong* seeded prior decays and is anchoring-flagged; multi-runbook seeds dedup/compete per 4.3), not a model judge. Run the sim/eval with strict-enforcement + average + cheap model (`claude-haiku-4-5`); confirm **no guarantee regression** (NO INCORRECT CONCLUSION, NO COLLAPSE UNDER PRESSURE), explicitly including a *misleading-runbook* scenario.
